# rag-kb-agent

只读本地 Obsidian 知识库的 RAG 问答 Agent。检索层做了粗排+精排两阶段与三段式证据门控，生成层是带 Function Calling 的 Agent Loop，并且对模型给出的每条出处做程序化对账。

这个项目是从 [`mini-agent`](../mini-agent) 演进来的正式版。mini-agent 保留不动，定位是学习轨迹仓库；本仓库是简历主菜。

---

## 一、架构

```
                    ┌──────────────── 离线：建索引 ────────────────┐
  Obsidian vault ──►│ 解析 md → 切块 v2 → bge-m3 向量化 → Chroma  │
  （206 个块）       └─────────────────────────────────────────────┘

                    ┌──────────────── 在线：检索层 ────────────────┐
  用户问题 ────────►│ ① 向量粗排  top 10（cosine）                 │
                    │ ② rerank 精排 top 6（bge-reranker-v2-m3）    │
                    │ ③ 证据门控  看 cosine，不看 rerank 分数       │
                    │      ├ none（<0.45）→ 不给材料，直接拒答      │
                    │      ├ weak（0.45~0.60）→ 给材料 + 警告自判   │
                    │      └ ok（≥0.60）→ 放行                     │
                    └──────────────────┬──────────────────────────┘
                                       │ 带出处的段落
                    ┌──────────────── 在线：生成层 ────────────────┐
                                       ▼
                    │ Agent Loop（MAX_STEPS=6）                    │
                    │   kb_search 语义主力                         │
                    │   kb_read   读全文                           │
                    │   kb_grep   关键词兜底                       │
                    │        ↓ 最终回答（每条结论标出处）           │
                    │ 引用校验：出处反查证据池，编造的当场告警       │
                    │ Trace：每步落 JSONL，可审计                   │
                    └──────────────────────────────────────────────┘
```

**一句话概括数据流**：粗排负责"别漏"，精排负责"排准"，门控负责"敢不敢答"，引用校验负责"答得是不是真有据"。这四件事用的是两套不同的分数，混用会出事（见第三节取舍 1）。

## 二、指标

评测脚本 `run_eval.py` 只测**检索层**，不测生成层——不调 LLM、不花钱、结果可复现。20 条 case 分布在四类：事实定位 8、语义改写 6、跨文件 3、拒答 3。

### 最终 A/B（`output/eval_report_ab_compare.md`）

| 指标 | 粗排 | 粗排+精排 | 变化 |
| --- | --- | --- | --- |
| Hit@3（文件级） | 82.4% | **94.1%** | ↑ 11.7% |
| Ans@3（答案级） | 82.4% | **94.1%** | ↑ 11.7% |
| MRR | 0.814 | **0.853** | ↑ 0.039 |
| 误拒率 | 0.0% | **0.0%** | → |
| 拒答拦截率 | 100.0% | **100.0%** | → |
| 漏网率 | 0.0% | **0.0%** | → |
| **总通过率** | 85.0% | **95.0%** | **↑ 10.0%** |

> Hit@k 只看"文件找对没有"；Ans@3 更严格，还要求该块正文真的含有期望关键词，即"找到了答案本身"而不只是"找到了那个文件"。

### 演进路径（三步，同基准可比）

| 阶段 | 门控 | 排序 | MRR | 漏网率 | 总通过率 |
| --- | --- | --- | --- | --- | --- |
| baseline | 单阈值 0.45 | 粗排 | 0.814 | 66.7% | 75.0% |
| +三段式门控 | cosine 三段 | 粗排 | 0.814 | 0.0% | 85.0% |
| +精排 | cosine 三段 | rerank | 0.853 | 0.0% | **95.0%** |

这张表里最值得看的是 **MRR 那一列**：第二步排序完全没变（0.814 → 0.814），总通过率却涨了 10 个点——说明这 10% **全部来自门控改造**；第三步门控没变，又涨 10 个点，这 10% **全部来自精排**。两个改造各贡献 10 个百分点，互不重叠，也不互相掩盖。

> **关于可复现性**：baseline 与 A/B 表里的粗排列是相隔 34 分钟的两次独立跑分，Hit@1（76.5%）与 MRR（0.814）**逐位相同**。纯向量粗排是完全确定的；有抖动的是 rerank（见失败分析 2）。

> **一份不同基准的旧报告**：`output/eval_report_baseline.md`（12:30）跑分在前、eval case 标注修正（12:43）在后，它的总通过率是 65.0%、MRR 0.784，**不能与上表直接比**。差值可以精确算出来：E14 标注修正后排名从 2 升到 1，MRR 应涨 (1/1−1/2)÷17 = 0.0294（0.784→0.813）、Hit@1 应涨 1/17 = 5.9%（70.6%→76.5%），与重跑结果完全吻合。留着它是为了记录这次标注修正的影响可被定量验证。

## 三、技术取舍

这一节是项目的核心。每条都写了"为什么这么选"和"另一条路为什么不走"。

### 取舍 1：排序用 rerank 分数，门控用 cosine 分数——两套分数各干各的活

这是整个项目最有价值的一个结论，而且是**先踩坑才得到的**。

第一版我把门控也接到了 rerank 分数上，结果排序大涨、门控崩塌：

| | 门控用 cosine | 门控用 rerank |
| --- | --- | --- |
| 误拒率 | 0% | 5.9% |
| 拒答拦截率 | 100% | 66.7% |
| 漏网率 | 0% | 33.3% |
| 总通过率 | **95.0%** | 85.0% |

诊断出两个具体反例：

- **E11**：正确答案的 rerank 分只有 **0.015**，被当成"没证据"误杀
- **E19**：一个完全无关的问题，rerank 分却有 **0.502**，直接漏网放行

rerank 分数在"能答"和"该拒答"两类上的重叠宽达 **0.487**；同样的两类在 cosine 上重叠只有 **0.086**。原因不难理解：reranker 是为"把最相关的排到最前"训练的判别模型，它的输出是相对排序信号，不是校准过的置信度，拿它当绝对阈值用属于误用。

所以最终形态是：`retrieve()` 里粗排之后**先记下整池最高 cosine**（`pool_cosine_max`），再交给 reranker 精排；门控只读 `pool_cosine_max`，排序只读 rerank 分。

```python
def evidence_score(hits) -> float:
    """门控看 cosine 不看 rerank：实测有正确答案只拿 0.015（E11），
    有无关问题却拿 0.502（E19），重叠宽 0.487。cosine 重叠只有 0.086。"""
```

**顺带一个容易写错的细节**：`pool_cosine_max` 必须在精排截断**之前**算。精排只留 top 6，如果截断后再取 max，拿到的是"精排后最高分"，而不是"整池最高分"，门控的语义就变了。

### 取舍 2：三段式门控，不是单阈值——单阈值在数学上无解

实测分数分布：

- 能答类（17 条）最低 cosine = **0.506**
- 拒答类（3 条）最高 cosine = **0.592**

单阈值 T 要同时满足「T ≤ 0.506」（否则误拒能答的）和「T > 0.592」（否则放过该拒的）——**矛盾，无解**。这不是调参问题，是两个区间本身重叠了 0.086。

实证（`output/eval_report_baseline_v2.md`）：取 T = 0.45 时，拒答类 3 条里只有 E18（0.445）被拦住，E20（0.464）和 E19（0.592）都过了阈值——**漏网率 66.7%**，即三分之二的无关问题拿到了「证据充分」的判定，直接成了幻觉的入口。把 T 往上提能堵住漏网，但立刻开始误拒能答的（E11 只有 0.506）。两头堵。

三段式把这个矛盾拆开了：

- `GATE_LOW = 0.45`：低于此，判定库里真没有 → 硬拒答，连材料都不给模型
- `GATE_SOFT = 0.60`：高于此，放心放行
- 中间 `0.45~0.60` 的模糊地带 → 给材料，但**附一句警告让模型自己判断**能不能支撑答案

约束条件是 `LOW ≤ 0.506` 且 `SOFT ≥ 0.592`，有解。中间那档的价值在于：把"机器拿不准"这件事如实交给模型，而不是假装自己能一刀切。实测 weak 档生效时（`output/smoke2.log`，问"我家猫的疫苗接种记录"），模型正确拒答，还主动说明了"最像的三段都无关、我没硬凑"。

### 取舍 3：rerank 走 stdlib urllib 直调 HTTP，不引新依赖

硅基流动的 `/v1/rerank` 端点不在 openai SDK 的封装范围内。两个选择：装一个 rerank 专用 SDK，或者用标准库 `urllib` 发一个 POST。

选了后者。理由是这个调用只有一个端点、一种载荷，引一个第三方包换来的是依赖表变长和版本冲突面变大，不划算。整个项目的运行时依赖只有 3 个（`chromadb` / `openai` / `python-dotenv`）。

### 取舍 4：rerank 挂了要退回粗排顺序，不能让检索跟着崩

精排是锦上添花。`rerank_hits()` 里 HTTP 失败会打印警告并原样返回粗排结果——宁可排序差一点，也不能让整条检索链路因为一个可选增强而挂掉。

### 取舍 5：`history` 只装问答对，但证据池是会话级的——两个不同尺度

跨轮记忆 `history` 只存「用户问题 + 最终回答」，中间的 tool_call 全部丢弃。原因是省 token，以及上一轮的旧检索结果会干扰这一轮判断（模型可能直接抄旧段落回答新问题）。

但引用校验的证据池 `evidence_pool` **反过来是整场会话累积的**，不清零。这个不一致是实测逼出来的：第 2 轮问"那它打算什么时候开始"，模型沿用了第 1 轮真检索到的笔记，如果证据池每轮清零，池子是空的，合法引用会被全判成编造。

累积之后误报消失，而真编造照样抓得住——实测模型引用的 `训练计划.md` 从头到尾没被任何一轮检索到，累积了也还是被揪出来。

### 取舍 6：eval 只测检索层，不测生成层

生成层要调 LLM，有成本、有随机性、不可复现，不适合当回归测试。检索层是纯函数（同样的库 + 同样的 query → 同样的排序），可以随便跑。

所以 `run_eval.py` 支持 `--both` 一次跑完 A/B 同场对比，改一次阈值就能立刻看到全部 20 条的升降。这个项目能做到"改一版跑一版、每版都有数"，靠的就是评测不烧钱。

### 取舍 7：切块沿用 v2（标题切主题 + 段内 500 字滑窗 overlap 80）

没有上语义切块。原因是探针数据显示当前瓶颈不在切块的"语义完整性"上，而在**长块稀释**上（见失败分析 1）——那是切块**粒度**问题，语义切块治不了它，反而更细的规则切块能治。把工程投入放在数据指出的方向上，而不是放在听起来更先进的方案上。

### 取舍 8：补上 requirements 里漏掉的 chromadb

mini-agent 的 `requirements.txt` 只有 `openai` + `python-dotenv`，**漏了 `chromadb`**（venv 里实际装的是 1.5.9）。后果是新克隆环境装完依赖跑不了建索引。这是个真实缺陷，本仓库补上并在注释里写明原因。

## 四、失败分析

不藏问题。下面每一条都是实测发现的，标注了当前状态。

### 1. E07 唯一未通过的 case：长块稀释【未解决】

问 embedding 模型相关的问题，正确答案 `bge-m3 / 1024维` 埋在《项目看板》一个几百字的长 bullet 里。粗排排不上去，精排也救不回来——探针实测 E07 在 rerank 前后都没进 top。

**病因**：一个块里塞了多个主题，向量化时被平均掉了，局部关键信息的信号被稀释。

**能治的方向**：更细的切块（按列表项/句子切）+ 给每块加标题路径前缀（如 `项目看板 › 秋招求职 › 技术栈`）来补偿丢失的上下文。这是下一轮的主要工作。

### 2. rerank 有轻微非确定性【已确认，接受】

同一份索引、同一批 case，两次跑分结果不完全一样：Hit@1 从 82.4% 变 76.5%，MRR 从 0.882 变 0.853，E13 从 rank 1 掉到 rank 2。

**处理方式**：README 和报告里都只看趋势和总量（总通过率、Hit@3），不抠单条 case 的名次。服务端排序有抖动是正常的，把它当成噪声而不是 bug。

### 3. 模型会编造出处标题【已加检测，未做自动修复】

强制要求标出处之后，出现了一个新的幻觉面：**模型会编出不存在的标题**。

实测一例：回答里写「来源：使用说明.md › 目录结构」，而《使用说明》根本没有"目录结构"这个标题——文件名对，标题是它自己加的。

**当前处理**：`check_citations()` 把回答里的每条出处拿去和真实检索结果对账，对不上就当场打印告警并记进 trace 的 `bad_citations` 字段。把静默幻觉变成了可见告警，且**不额外调 API**。

**没做的**：还没做"检测到编造就反馈给模型重写一轮"。目前是告警但不阻断。

### 4. 引用校验器自己也有 bug【已修】

值得单独记一笔，因为它是"检测幻觉的代码本身产生了幻觉"。

最早的正则是 `r"来源：([^）)\n]+)"`，遇到第一个右括号就截断。可笔记标题里带全角括号是很常见的形态——实测 `项目看板.md › 健身计划（⏸ 暂缓）` 被截残成「健身计划（⏸ 暂缓」，和真实检索结果对不上，**把合法引用误报成了编造**。

修正为允许标题内含一层配对括号（全角/半角都支持）。离线自检 5 条用例全过，含嵌套括号的多出处也能完整抓取。两层以上嵌套不支持——实际数据里没出现过，不为不存在的情况加复杂度。

### 5. Windows 控制台编码坑【已修，环境相关】

两个坑，都不是代码逻辑问题但都会让程序直接崩或输出乱码：

- 控制台默认 GBK 码页，`✅ ❌ ›` 这类字符会抛 `UnicodeEncodeError` → 在 `run_eval.py` / `agent.py` 顶部 `sys.stdout.reconfigure(encoding="utf-8")`
- PowerShell 5.1 的 `$OutputEncoding` 默认 ASCII，管道把中文传给 Python stdin 时会先变成一串问号 → stdin 也要 reconfigure，且调用方需设 `$OutputEncoding = [System.Text.UTF8Encoding]::new()`

## 五、快速开始

```powershell
# 1. 装依赖
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt

# 2. 配环境变量：复制 .env.example 为 .env，填入 API key
#    需要 SILICONFLOW_API_KEY（向量+精排）和 DEEPSEEK_API_KEY（生成）

# 3. 建索引（读 NOTES_DIR 指向的 vault，写入 chroma_db/）
.venv\Scripts\python build_index.py

# 4. 跑评测（不调 LLM，免费可复现）
.venv\Scripts\python run_eval.py --both --tag my_run

# 5. 对话
.venv\Scripts\python agent.py                     # 连续对话模式
.venv\Scripts\python agent.py 我的六级什么时候补考   # 单问模式
```

可调环境变量（都有默认值，见 `.env.example`）：

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `TOP_K` | 6 | 精排后送给模型的块数 |
| `RERANK_POOL` | 10 | 粗排召回给精排的候选数 |
| `USE_RERANK` | true | 关掉即退回纯粗排（A/B 对照用） |
| `GATE_LOW` | 0.45 | 低于此硬拒答，须 ≤ 能答类最低分 |
| `GATE_SOFT` | 0.60 | 高于此放行，须 ≥ 拒答类最高分 |

## 七、和 mini-agent 的区别

| | mini-agent | rag-kb-agent |
| --- | --- | --- |
| 检索 | 单阶段向量召回 | 粗排 + rerank 精排 |
| 门控 | 单阈值二元 | 三段式（none / weak / ok），cosine 尺度 |
| 元数据 | 文件名 | 文件名 + 标题路径（出处可精确到小节） |
| 评测 | 无 | 20 条 case + A/B 跑分脚本 |
| 引用 | 要求标出处 | 要求标出处 **+ 程序对账，编造的当场告警** |
| 展示/检索 | 耦合 | 解耦（`retrieve()` 返回结构化结果，展示交给调用方） |
| 依赖 | 漏了 chromadb | 补齐 |

mini-agent 的 README「已知限制」里列了两个进阶课题：rerank 和语义切块。本项目做了前者，并且用探针数据说明了为什么暂时不做后者（取舍 7）。
